Two paths, one project

Path A – I calculate risk metrics myself

  • Build historical VaR from position data and market returns
  • Compute my own component VaR, factor exposures, concentration
  • Doable. I'm prepared to do it.
  • 3-4 weeks building a crude approximation of what the risk system already does
  • My VaR won't match the desk's VaR
  • Can't compute real utilization without knowing the limits

Path B – Read access to risk cube outputs

  • The risk system already computes everything I need every night
  • Reading outputs only, not writing, not touching production
  • Zero engineering cost to the desk
  • This is the version that tests the theory with the real measurement
  • This is the version that can't be done anywhere else
Path A means testing the theory with a self-built proxy, which is essentially what external researchers already do with Fed Z.1 data. The entire reason to do this project here is to use the real thing.

What I'm asking for

Data request (bounded and specific)

  • Daily firm-level or desk-level VaR with component breakdown by asset class
  • At least one of: scenario P&L, factor-VaR decomposition, or VaR utilization
  • Historical depth: as far back as available (5 years ideal, 2-3 workable)
  • Frequency: daily, end-of-day, after the nightly risk run
  • No write access. No production changes. No real-time feeds.

I understand this data is sensitive.

I don't need positions, trades, or P&L. VaR is already an aggregated output that reveals nothing about individual strategies.

I can work at whatever level of aggregation you're comfortable with.

Raw numbers never appear in any deliverable. Outputs are statistical properties (IC, Sharpe, SHAP rankings), not dollar amounts.

VaR utilization (usage vs. limit) is the single highest-value feature. It's the direct measurement of the constraint the theory says drives everything. If access isn't workable, I'll build my own metrics and test the same hypothesis. If the self-calculated version shows something, that's a reason to revisit.

How I make sure the results are real

What Kills ProjectsHow This Project Handles It
Data snooping Every experiment logged. Deflated Sharpe Ratio (Bailey & Lopez de Prado 2014) adjusts for total number of things tried.
Overfitting Ridge regression baseline on every test. If the ML doesn't beat a linear model on the same features, it added nothing.
Lookahead bias Point-in-time stamping on every feature. Holdout reserved on day one, untouched until the final test.
"Can you trade it?" Transaction costs in every backtest from the start. Sharpe reported gross and net. Breakeven cost calculated.
Unstable features Feature importance checked across all CV folds. If a feature flips sign between folds, it gets flagged and dropped.
Validation infrastructure is ~25% of total project time. Built before touching any signals. ~45 independent trials exhaust a Sharpe of 1.0 on 5 years of data (Bailey-Borwein-LdP 2014). Every trial is counted.
