## Constraints that decide which features are even possible

Read these first. Three of them kill the obvious ideas.

| Constraint | Consequence |
|---|---|
| **No model in the page** | No free-text grading, no "explain in your own words" scored. Anything graded must be machine-checkable against an embedded key. |
| **Answer keys come from `survey.json`**, never the model | Every new question needs a deterministic source: the import graph, git churn, the captured command runs, or the resolved anchors. If you cannot derive the key from static analysis, the question does not ship. |
| **Contract `trailhead/verified@1` is frozen** | The 8 block types and 4 checkpoint kinds (`single`, `multi`, `order`, `file-pick`) are the vocabulary. Prefer features that fit them. | One file, zero external requests, `localStorage` only | State is per `repo:commit`. No server, so no cross-device history and no real spaced-repetition scheduler. Spacing has to happen *within* the 90 minute session. |
| Never cut | Claim markers, the audit panel, the dropped-claim count. |

## What the research actually says

**Learning science.** The findings that bear on this artifact:

- **Retrieval practice beats rereading.** Testing yourself is the study activity, not the assessment of it. Every stop should ask before it tells at least once.
- **Parsons problems** (drag mixed-up code into order) produce the same learning as writing the equivalent code at *higher efficiency*, and are more sensitive than code-writing for measuring comprehension. They test whether you understand meaning and sequence. Ericson's **intra-problem adaptation** (make it easier after repeated failure) reduces frustration without reducing gains.
- **Predict, then observe.** Committing to a prediction before seeing output creates the error signal that makes the correction stick. Free, because the command runner already captured the real exit codes and stdout.
- **Worked examples, then fading.** Full guidance first, then progressively remove steps and make the learner supply them. The trace stop is the natural home.
- **Cognitive load.** Watch the *split-attention effect* (narration must sit next to the code it describes, not in a separate panel) and the *redundancy effect* (do not restate in prose what the excerpt already shows). **Signaling**, meaning explicit cues about where to look, is what the focus lines already do.
- **Desirable difficulties.** Interleaving and spacing feel worse and work better. Do not smooth the path.

**Interactive explanation design.** Bret Victor's distinction is the one that matters: an explorable explanation is not a widget, it *deliberately guides attention* toward particular phenomena. The map today is a free-exploration widget with no attention direction. Nicky Case, Bartosz Ciechanowski and Distill are the reference bar for craft.

Matuschak and Nielsen's **mnemonic medium** (Quantum Country) is the closest prior art: prompts interleaved directly into prose, not bolted on at the end. Their six rules for a good prompt are the checkpoint spec you are missing:

**focused** (one detail), **precise** (vague questions get vague answers), **consistent** (same answer every time), **tractable** (aim ~90% correct), **effortful** (the answer is retrieved, not read off the page), **well-scoped**. Beyond recall, they distinguish *explanation* ("why") and *application* (transfer) prompts.

Audit the four existing checkpoints against those six rules before adding any more.

## Features, ranked by value per hour

Ship in this order. Stop when the time budget runs out, not when the list ends.

1. **Predict-then-reveal on command blocks.** Before showing `exit 0 / 41.2 s`, ask "will this pass?" Two options, key is the captured exit code. Reveal on answer. This is the highest ratio in the list: the data is already in `verified.json`, it needs no new key source, and it turns the two real failures from a curiosity into the moment the reader learns what a broken checkout looks like.
2. **Predict-then-reveal on trace hops.** At hop N, ask which file the call goes to next, `file-pick` from the real module list. Key is the next hop's anchor. This is worked-example fading applied to the trace: hops 1 and 2 fully narrated, 3 onward ask first.
3. **A recall strip at the top of each stop.** One `single` question drawn from a stop two or three back, keys from `survey.json`. In-session spacing, which is the only spacing a file with `localStorage` can do. Keep it to one question so it stays a warm-up, not a gate.
4. **Guide attention on the map.** Add a short ordered tour: three or four steps that highlight one node at a time with a sentence about why it matters, then release to free exploration. Victor's point, directly applied. Reuses the existing node highlight and drawer.
5. **Adaptive Parsons.** The `order` kind already exists. After two wrong submissions, lock the one position the learner has correct and say so. Ericson's intra-problem adaptation, roughly 20 lines.
6. **Confidence capture.** Ask "sure / not sure" alongside each checkpoint answer and show a calibration line in the audit panel: "you were confident and wrong 3 times." Cheap, machine-checkable, and it rhymes with the pitch, since the whole artifact is about calibrated trust.
7. **Self-explanation, ungraded.** Before revealing an anchor, offer a textarea: "what do you think this does?" Store locally, reveal the real excerpt beside it, never score it. This is the honest way to get the self-explanation effect with no model in the page. **Label it clearly as not graded** so it does not read as a broken feature.

Not worth it here: a real spaced-repetition scheduler (needs cross-session storage and days, not 90 minutes), anything requiring free-text grading, and gamification (points, streaks, badges) which reliably crowds out the intrinsic goal.

## Rules while you build

- Every new question states its `provenance` and shows it after answering, same as the existing checkpoints. A question whose key you cannot trace to `survey.json` or a captured run does not ship.
- Immediate feedback, explanation shown whether right or wrong.
- Scores stay local, visible only to the learner, resettable. This is not a test and must not read as one.
- Keyboard operable, visible focus, works under `prefers-reduced-motion`, survives print.
- Prefer extending an existing block type over inventing one.
